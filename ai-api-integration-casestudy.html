AI and API Integration Case Study

Safe AI Integration for a Commission and Payroll CRM

AI is a guest. The rules stay yours. How I let outside software and AI agents read and write a live pay system without ever breaking payroll.

800+ active users

1 Rule Set for App and API

The Question That Started It

A US field-sales startup asked me a simple question. "Can our other software talk to our data?"

The data was not simple. It lives in the custom CRM I built for them, with 800+ active users, and it holds commissions, payscales, approvals and payroll. One wrong write in a system like that is not a bug. It is a wrong paycheck.

So I built the API the careful way. Read first, writes later, and every write behind the same locks the office already trusts. Then the client tested it live through Claude, and the rules held.

Client

A US field-sales startup. Name kept confidential.

Scale

A custom CRM with 800+ active users across web and iOS.

My Role

Solo developer, end to end. Design, build, security and docs.

Stack

Next.js and Supabase, with Postgres row level security.

The Problem Before the API

The CRM already ran the business. Reps reported sales, vendor files were imported and matched, managers set payscales, and payroll ran from the system.

Before the CRM, commissions and approvals ran across spreadsheets and messages, and managers had no single view of what their reps were still owed. The CRM fixed that inside the app. But the data was still locked inside the app.

The client wanted their other tools to pull data out, and then push data in. Products, orders, invoices and pay plans. And they wanted AI in the loop.

That is where the real risk sat. Write access to a pay system is dangerous. One bad sync or one retry on a weak network could create a duplicate order, edit something already paid, or move a money row nobody approved. If an AI agent is the one calling the API, it can make those mistakes faster than any person.

The question was never "can I build an API". It was "can I let outside software, and AI, touch this data without ever breaking payroll".

The Bottleneck in Pay and Commission

Pay Rules That Spreadsheets Cannot Hold

Commission in field sales is not one rate on one line. Managers set rates per vendor, product and amount. One sale can have a trigger rep, who made it, and a receiver rep, who gets paid. Same person is a normal commission. Different person is a split, an override or a bonus. Rates have start and end dates, so a rate change never rewrites last month.

On top of that sit approvals. Managers approve per customer or product before admin runs payroll. I found and fixed a partial approval bug that "select all" testing had hidden, and a silent 1,000 row truncation that would have made totals wrong at scale. Both taught me the same thing. Pay logic only holds when it lives in one place and is tested at the grain people actually approve at.

Locks After Payroll

Once payroll runs, the past has to be read only.

  • A processed order cannot be edited or deleted. The money already went out.
  • An approved order can change its name, references, status and rep, but not its product or sale date, because those drive the pay amount and the pay period.
  • Ledger rows are never rewritten. A correction is a new row, so the trail always adds up.
  • Commission, override, holdback and payment batches stay in the app with a person.

These rules already lived in the commission finance engine. Any API had to obey exactly the same rules, or it would become a back door around payroll.

Imports That Decide Who Gets Paid

Vendor files decide commissions, and vendors do not report the same way. I rewrote the import pipeline 3 times because of that. Matching uses hard IDs first and a soft fallback second, so commissions do not double. After a snapshot redesign, imports that took 10 to 12 minutes now process 6,000+ records in under a minute.

An API that writes orders sits right next to this pipeline. A careless integration could undo all of that work in one sync.

Training Issues That Turned Into Pain Points

Field reps are selling experts, not technology experts. That is a principle I build around, and it showed up everywhere.

Reps Needed Help Getting In

New reps tried to sign in before they had an account. Some signed up with a different email than the admin typed. I replaced docs with a visual 4 step guide and linked accounts by code instead of email.

Managers Had Rules to Remember

Who can see a rep's sales, who can touch their pay, which rates are locked by admin. I moved those rules into the system. Managers can never edit their own payscale, and seeing sales is a separate permission from touching pay.

Rules Lived in People's Heads

Payroll review used to depend on fragile formulas, private files and scattered manual notes. When a rule lives in someone's memory, every new hire, manager and tool has to be trained on it, and every mistake becomes a pay dispute.

Onboarding Carried a Real Cost

Getting a field org onto new software was a support burden in itself. About four people struggled to train reps and managers, and every rule that stayed outside the system meant more explaining, more questions and more room for error.

Today that load has dropped significantly. AI now handles that training better than the old manual effort did, and it does it through the guarded API, so it works inside the same rules the system already enforces.

This is exactly why AI made the client nervous and excited at the same time. An AI agent is the newest hire of all. If the rules lived in people's heads, the AI would need to be trained on them too, and it would get them wrong. The rules had to live in the server, where no person and no model could skip them.

The Solution, a Safe AI Integration

A Guarded API First

I shipped it in the boring, safe order. Read only first. An admin opens an API tab, sees the company ID, and creates or rotates one key. The key is shown once and stored only as a hash. The key and company ID must match in one lookup, and a wrong pair always gets the same "Invalid credentials". Every query is forced to that company's data, and rate limits are stored in the database, not in memory, because memory limits do not survive on serverless.

Then writes, behind guardrails.

  • One key, scope chosen on purpose. Read, or Read plus Write. Read only is the default.
  • A company level write switch. Write stays off until it is turned on for that company, and the server checks it on every write call. Turning it off stops existing write keys immediately.
  • Idempotency key on every create. A retry returns the saved response and changes nothing, so a weak network never means a duplicate order.
  • Strict body allowlist. Unknown fields are rejected, not ignored. Payroll flags, paid dates, auth fields and customer personal data are blocked. The company is never taken from the request body.
  • Ownership check on every ID. A vendor, product, order or rep from another company returns "not found", so nothing leaks.
  • Some actions are human only. The API can never mark anything paid. There is no invoice delete, only void. Pay plans can be viewed and edited, but never created over the API, because a new pay plan is a business decision.
  • Response guard. Every response is scanned for forbidden fields before it leaves the server.
  • Old integrations keep working. The read only version is frozen, and old keys simply get "forbidden" on writes.

The most important decision was simple. The API and the app share one rule set. The same guard decides "is this locked?" for a manager in the dashboard and for a call through the API. An integration can never do something a manager in the app could not do.

AI Agnostic, No Lock In

Once the guarded API exists, the AI on top of it becomes replaceable. Connect ChatGPT today. If it has issues, switch it off and plug in Claude, Grok or Gemini. The system stays exactly the same, and exactly as safe, because the safety was never inside the AI. It is inside the API.

This is not theory. The client ran their live test through Claude. The same guarded API is built to work the same way with ChatGPT, Grok or Gemini, because any model that can call an API goes through the same rules. The founder picks the tool. The rules do not change.

AI Acts as a Guest

I treat an AI agent like any untrusted integrator. It gets a scoped key, idempotency, the allowlist, the payroll locks and the audit trail. Nothing more. The AI can try anything. The server rules decide what actually happens.

Every API write is recorded separately from human writes, so it is always clear what came from a person and what came from an integration. Business events, like a key being created or an order being updated, are kept as permanent history. Noisy traffic events, like failed auth or rate limits, are cleared after 90 days.

200 Reads and Writes a Minute

Safe does not have to mean slow. At first, agents could do about 37 to 40 reads and writes a minute. I raised that to up to 200 reads and writes a minute per agent setup, and every agent on the company's setup can use it, all inside the same locks and audit trail. Rate limit raised from about 40 to 200 a minute (5x higher).

The other limits still apply. There are separate buckets per key, per company and per IP, and write buckets are smaller than read buckets. A runaway sync gets stopped with a "too many requests" response before it can flood payroll data.

The Founder Owns the System

The founder does not depend on any AI. The CRM is theirs, built around their own pay rules, payscales, imports and approvals, and it works fully without AI.

AI is an add on that makes the system more efficient. It can help with the work, but it cannot run the business, and it cannot quietly harm the records. If the founder wants to change a rule, they change it in their system, and every person and every AI follows it from then on.

Why Blind AI Writes Are Dangerous

A lot of companies plug an agent straight into their CRM or database. It works in the demo. Then it gets one change wrong.

Wrong Pay

An agent edits a product or sale date on an approved order, and the pay amount or pay period shifts.

Overwritten Records

A "fix" rewrites a ledger row instead of adding a correction, and the history no longer adds up.

Duplicate Changes

A retry after a timeout creates the same order or invoice twice.

Edits to Money Already Paid

A processed order or a paid invoice gets changed after the fact.

No Trail

Nobody can tell who changed what, a person or a bot, or when.

Blocked by Design

Every one of these is blocked in the guarded API. Not by asking the AI to be careful, but by making the wrong action impossible.

Results and Proof

Live AI Test Passed

The client drove the read and write API through Claude in a live session. Data moved between their tools, and the guardrails decided what was allowed. Creating and editing orders worked. Marking anything paid, or editing locked or already paid records, was blocked. Payment allocation stayed with a person.

Rate limit raised from about 40 to 200 a minute (5x higher)

From roughly 37 to 40 reads and writes a minute to up to 200 a minute per agent setup, with no change to the locks or the audit trail.

One Rule Set, No Back Door

The app and the API call the same guard helpers, so a lesson learned once protects every path in.

No Breaking Changes

The read only version and old keys kept working while writes were added.

Shipped in Small Safe Steps

Schema, scope settings, core library with unit tests, products, orders, invoices, and docs last. Each step deployable on its own.

Support Load Dropped Significantly

About four people used to struggle to train reps and managers. Now AI handles that training better, through the guarded API and inside the same rules.
